# blindbuild v0.6 — planner in Claude Code, builder launched by the planner

Status: approved by Yashar · 2026-11-21 · author: Yashar (decisions), Claude (write-up)

## 1. Intent and why

blindbuild splits the work between a **planner** (holds the plan, talks to the user, reviews results) and a **builder** (implements one work order, never sees the plan). Yashar believes this separation is what produces higher-quality code, and it is the one thing v0.6 must not weaken.

Real use of v0.5 on a second machine exposed four failures:

1. **The planner could not wake up.** It lived in a Cowork chat. A scheduled task runs as a separate session and cannot reach the chat; a `sleep` loop blocks the chat so the user's messages go unread.
2. **The builder did not stay up.** `loop.mjs` exits the whole loop after any run that "needs attention" (a question included) and after `max_runs`. The user had to restart it by hand.
3. **No `gh` or local tools.** The builder's allow-list has no `gh`, so it is silently denied in headless mode. Cowork's shell is a sandbox that never sees the user's `gh` login.
4. **Work ran one ticket at a time.** The builder skill builds alone below 3 tickets; parallelism only happened when the user demanded it, and simple jobs took hours.

What Yashar values from Cowork: a UI that reports back, and the planner/builder separation. Neither requires Cowork (see §4).

A colleague's package (plain Claude Code skills, interactive, on the user's machine) used `gh` with zero setup. That confirmed the cause of problem 3: where the shell runs, not the plugin.

## 2. Goals, non-goals, anti-goals

**Goals**
- The planner runs in an interactive **Claude Code** session on the user's machine and reports **in that chat**.
- The planner launches the builder itself; the user never runs a start script during normal use.
- The planner wakes on its own when the builder finishes, asks a question, stalls or crashes, without blocking the chat.
- The user can **watch the builder live** in a separate window, including which agent is doing what.
- Independent tickets run in **parallel by default**.
- The builder can use read-only `gh`; denied tools are visible, never silent.
- Screenshots dropped in the planner chat reach the builder.

**Non-goals (v0.6)**
- Cowork as planner. It may keep working, but it is no longer supported or tested.
- Typing into the builder mid-run ("take over" mode). Revisit only if real use demands it.
- Overnight runs with the planner session closed. The builder survives a closed planner, but reviews wait until it is reopened.

**Anti-goals (failure even if it "works")**
- Anything that lets the builder see the plan, or lets the user's typing leak into the builder.
- A chat blocked by sleeping or polling.
- A run that looks successful but did nothing (the spike found one: an unauthenticated `claude -p` returns `subtype: success` with `is_error: true`).
- Silent permission denials.

## 3. Constraints

- Everything in v0.5 that protects the user stays: main never touched, base branch, `accept` by the user only, locked 19 rules, guard hook, plan folder outside the repo, no AI evidence in git, DB `--confirm` flow, stable copy.
- Node 18+, no dependencies. Windows, macOS, Linux. Windows paths and argument quoting must be handled explicitly (spike failure: an unquoted `wt --title` split on a space).
- Claude Code version-sensitive features (stream-json events, background-command notifications, subagent IDs in the stream) are checked at setup, with a stated fallback.
- The builder stays headless (`claude -p`, `dontAsk`, locked settings file).

## 4. Approaches considered

| Approach | Trade-off | Decision |
|---|---|---|
| A. Planner in Claude Code, a background waiter (`bb wait`) wakes it | Clean, but relied on an unproven wake-up | Folded into D |
| B. Claude Code `/loop` polling | Up to N minutes late, tokens spent on empty checks | Fallback only |
| C. Keep the Cowork planner, add a bridge for `gh` | Keeps the UI but wake-ups stay manual, which is the original failure | Dropped |
| Headless planner | Works, but has no chat to report into | Dropped |
| **D. Planner in Claude Code launches the builder as an independent headless process; a background waiter wakes the planner; a watch-only viewer shows the run live** | Needs the planner session open for reviews; relies on a background command waking an idle session | **Chosen by Yashar** |
| Headed (interactive) builder | Breaks the exit signal, can stall on prompts, leaks the user's typing into the builder | Rejected; possible later "take over" mode |

**Spike (2026-11-21, Yashar's laptop, Claude Code 2.1.197) proved D's risky parts:**
1. An idle interactive planner woke by itself when a background `node wait.mjs` exited after the builder posted. PASS.
2. `claude -p --output-format stream-json --verbose` streams live events. PASS. Unexpected event types appeared (`rate_limit_event`, `system/thinking_tokens`).
3. A viewer in a new Windows Terminal tab. Failed on argument quoting (two error windows); fixed and relaunched.
4. A builder launched detached survived its parent exiting. PASS.

Plus two setup findings: the CLI was not logged in (and headless runs hid it), and an interactive session shows a one-time "trust this folder?" prompt.

## 5. The design (decided parts)

### 5.1 Roles and where they run

```
You ⇄ Planner (interactive Claude Code, in the repo, real shell: gh, git, connectors)
          │ writes work order → .devteam/mail/to-builder.md (+ attachments/)
          │ launches → bb run   (detached; returns at once with a run id)
          │ background → bb wait <run>   (exits on: summary ready · stall · crash · timeout)
          ▼
      Builder (headless claude -p, locked settings, stream-json → runs/<id>/stream.jsonl)
          │ lead + parallel developers + reviewer, one feature branch
          ▼ result → .devteam/mail/to-planner.md, then the process exits
      Supervisor (re-runs gate, commit and scope checks → runs/<id>/summary.json)
      Viewer (bb watch <run>: separate window, read-only, replayable)
```

### 5.2 Launching the builder (`bb run`)
- Starts a detached **supervisor** (a small Node process) and returns at once with the run id. The supervisor runs `claude -p`, and after it exits runs the v0.5 evidence checks itself: gate re-run (`gate.log`), new-commit check, scope check against owned files. Then it writes `summary.json` and `last-run.json`. *(Claude's call: keeps "trust evidence, not claims".)*
- The supervisor is started **detached** (`detached` + `unref` on all OSes; hidden on Windows), so closing the planner, the viewer or a terminal never kills it.
- Writes `runs/<id>/run.json` (pid, started, work order id) and streams to `runs/<id>/stream.jsonl`.
- Opens the viewer window unless the profile sets `viewer: "off"`. Windows: Windows Terminal with every argument quoted, then `cmd /c start`. macOS: Terminal.app via `osascript`. Linux: `x-terminal-emulator` if present. Any failure: print the `bb watch` command. *(Claude's call for macOS/Linux: one launcher each, printed command as the safety net.)*
- Refuses to start if a run is active, the tree is dirty, the rules hash fails, or `claude auth status` reports not logged in (all with a plain-English reason).
- Replaces the v0.5 `start` loop. `bb start`/`stop` remain as a deprecated alias for one version.

### 5.3 Waking the planner (`bb wait <run>`)
- The planner starts it as a **background** command and ends its turn. Exits with a one-screen summary when the supervisor has written `summary.json` (so the gate log and scope check always exist before the planner reviews), the supervisor or builder dies without a summary (crash), the stream is silent for `stall_minutes` (default 10), or `max_wait_minutes` (default 30) passes (prints "still running; last activity …", and the planner re-arms).
- The exit output tells the planner which case it is, so the planner's next action is never a guess.
- The planner skill states the rule: one waiter at a time; never `sleep`; never poll in the foreground; never create scheduled tasks for check-ins.
- Fallback if a Claude Code version doesn't wake idle sessions: the viewer shows a green "DONE, tell the planner" line and the OS shows a notification.

### 5.3b Recovery when a run goes wrong (decided by Yashar)

Applies in the **autopilot** preset; **assisted** and **manual** ask before every recovery.

| What happened | Planner's action |
|---|---|
| Not logged in (`authentication_failed`) | Always asks the user. Only the user can log in. |
| Rate limit | Waits for the reset, then relaunches by itself. |
| Builder crashed | `halt` (rescue branch), relaunches **once** by itself; a second crash → asks the user. |
| Stall (no activity for `stall_minutes`) | Asks the user before halting. A long test suite can look like a stall. |

Guarantees: never two builders at once (run lock); `bb wait` never kills anything.

### 5.4 Viewer (`bb watch <run>`)
- Reads `stream.jsonl` and the agent status files; read-only; reopenable and replayable at any time.
- Top: a **status board**, one line per agent (`[lead]`, `[dev-T1]`, `[reviewer]`) with state (working, BLOCKED, DONE, FAILED), last action, and seconds since last activity.
- Below: a live activity feed. Known events become readable lines; unknown event types are skipped, never crash it.
- **Denied tool calls in red**, with the exact command.
- End of run: a green or red summary line.

### 5.5 Agent status (Yashar's request)
- Activity is derived automatically from the stream, attributed by the agent ID each event carries.
- Each agent also writes its own `runs/<id>/agents/<agent>.json` at three moments: `started`, `blocked` (with what it needs and why), `done` (one-line summary). One file per agent, so no collisions; the guard allows these writes and nothing else under `runs/`.
- A blocked developer stops and reports; it never waits. The lead collects blocked tickets and puts one consolidated question in the result.

### 5.6 Builder stays useful (fixes failure 2)
- One work order = one launch. Questions end the run cleanly with a result; the planner answers (or asks the user) and launches again with the answer appended. Nothing for the user to restart.
- The result format gains a `Run status` field: `done`, `question`, `blocked`, `failed`.
- `authentication_failed`, `is_error: true` and rate-limit stops are detected from the stream and reported as such, never as a generic crash.

### 5.7 Parallel by default (fixes failure 4)
- The builder skill's default flips: **two or more independent tickets → parallel developers** in waves, up to `max_parallel_devs` (default 3). Building alone needs a stated reason in the result.
- The planner skill writes work orders as independent tickets with owned files by default, so parallelism is possible.
- Verify and fix `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS=0`: if it cuts off subagents in `-p` mode, remove or raise it.
- The result reports per-ticket timing, so slow sequential runs are visible.

### 5.8 Tools (fixes failure 3)
- Builder: read-only `gh` allowed by default (`gh pr view|list|diff|checks`, `gh run view|list`, `gh issue view|list`, `gh repo view`, `gh api` GET only via a guard check). `gh pr merge|create|close`, `gh release`, and `gh api -X POST/PATCH/DELETE` stay blocked by the guard.
- Profile `builder.allowed_commands` remains the user's way to add more; the planner proposes additions when the viewer shows a denial.
- Planner: runs in the user's real shell, so `gh`, git and Claude Code connectors work as in any interactive session. Its writes are still limited to the plan folder and `.devteam/mail`.

### 5.9 Screenshots and attachments
- The planner saves dropped images to `.devteam/mail/attachments/<work-order>/` and lists them in the work order with one line each on what matters in the image.
- Images dragged in, or given as a path, are copied by the planner. A screenshot **pasted** from the clipboard has no file on disk in Claude Code, so the planner asks the user to save it as a file (or drag it in), and meanwhile describes it in words in the work order. *(Claude's call: avoids depending on Claude Code's internal image cache, which varies by version.)*
- The builder reads them with its Read tool. Attachments are excluded from git like the rest of `.devteam/`.

### 5.10 Setup (preflight, borrowed from the colleague's package)
Setup checks and reports. It never installs silently:
- `claude auth status` → logged in.
- `claude --version` → at or above the tested minimum; stream-json flags work (one cheap real run).
- `git`, `node`, `gh auth status` (optional: missing `gh` disables the gh features, with a note).
- Opens the planner once in the repo so the user answers the folder-trust prompt while present.
- Commit signing works unattended (existing check).
- Windows: Windows Terminal present (optional).
